### `AgentId` / `Scheme` 为什么能直接删

| 字段 | 原注释 | grep 结果 |
|---|---|---|
| `AgentId` | 微应用ID(用于JSSDK鉴权) | **0 处引用** |
| `Scheme` | 客户端回调协议，如 `beaver://` | **0 处引用**；`getoauthconfiglogic.go` 用的是 `oauth.Desktop.CustomScheme` |

→ 两者都是「客户端微应用」维度的遗留字段，从未被使用。如将来要做 JSSDK 鉴权，应**独立成表**，不要塞回 `OpenApp`。

### 能力开关为什么全删了（`EnableRobot` / `EnableOAuth` / `EnableWebhook`）

> 尺子：**只管数据表**，不看逻辑引用。

三个字段混了**两种语义**，这就是它们的问题所在：

| 语义 | 含义 | 真相在哪 |
|---|---|---|
| **已开通**（派生） | 该能力当前生效中 | 能力表的 `Status` / 记录存在性 |
| **被允许**（独立策略） | 平台允许该应用使用此能力 | 只能存在应用表（它是唯一真相） |

三个都属于「已开通」—— **都能从能力表推出来** → 全部删除：

- `EnableRobot` → 看 `OpenRobot` 记录 + 其 `Status`
- `EnableWebhook` → 看 `OpenAppEventSubscription` 记录 + 其 `Status`（该表已一并删除，见零节第 7 行）
- `EnableOAuth` → 看 `OpenOAuthConfig` 记录 + 其 `H5/Desktop/Mobile.Enabled`

> 若将来真需要「平台允许某应用使用某能力」这种**策略**，那是独立事实，应独立成表，而不是塞回应用表当布尔列。
> （此前记为"保留"，理由是鉴权路径依赖；按"只管数据表 + open 模块正在重构"的约定，该理由不再成立。）

**仍未处理的**（见第三/四节）：`OpenBotModel.Name`（与已删的 `RobotName` 属同类复制）、`OpenOAuthConfig` JSON 列类型（`text` vs `json`）、`OpenOAuthQrCode` 基类（手写字段 vs `gorm.Model`）、时间戳类型统一。

> ⚠️ 删除字段会使读取处编译不过，按约定**逻辑层后续再改**。

## 一、判定标准（10 条尺子）

| # | 检查项 | 不合格的样子 |
|---|---|---|
| 1 | **重复** | 同一事实在别处已有（如 `RobotName` 与 `UserModel.NickName`） |
| 2 | **派生冗余** | 可由其他数据推出却存了一份 |
| 3 | **该引用却复制** | 该存 ID 的地方存了完整字段 |
| 4 | **类型不当** | 时间戳用 `int64` 而非 `datetime`；枚举用裸 `int` 无常量；JSON 列类型标注不统一 |
| 5 | **可空性错误** | 业务必填却没 `not null`；用空串代替 `NULL` |
| 6 | **索引问题** | 高频查询字段无索引；或索引冗余（`uniqueIndex` 已覆盖普通 `index` 的作用） |
| 7 | **缺约束** | 该唯一的不唯一；该有复合唯一键的没有 |
| 8 | **命名不一致** | `AppID` vs `AppId`；`Status` vs `State`；表名前缀不统一 |
| 9 | **基类/审计风格不一** | 同域内 `gorm.Model` / `models.Model` / 手写字段三种混用 |
| 10 | **敏感数据** | 密钥、令牌明文落库 |

**严重度**：🔴 结构性问题（该改） · 🟡 一致性/规范问题（可批量修） · 🔵 待确认（可能是刻意设计）

## 三、第一批：`open` 域 8 张表

### 3.1 `OpenApp`（应用主表）· 19 → 7 字段

> 尺子：**这个字段描述的事实，能不能从别处推出来？** 能推出来 → 删；推不出来 → 留。

**保留 7 个**

| 字段 | 为什么留 |
|---|---|
| `AppID` / `AppSecret` | 应用身份与鉴权凭据 |
| `Name` / `Description` / `Icon` | 展示信息（OAuth 授权页要显示"XX 应用请求访问…"） |
| `OwnerID` | 归属，只存 ID 不存资料 —— 正确 |
| `Status` | 只区分「能不能用」（启用 / 禁用）。**运营必需**：停用一个应用不该删掉它的数据和配置 |

**删掉 12 个（三轮）**

第一轮 · 死字段：

| 字段 | 删的理由 |
|---|---|
| `AgentId` | 死字段（0 引用）；客户端微应用维度，应独立成表 |
| `Scheme` | 死字段（0 引用）；真正在用的是 `OpenOAuthConfig.Desktop/Mobile.CustomScheme` |

第二轮 · 能力的第二份真相 + 孤儿字段：

| 字段 | 删的理由 |
|---|---|
| `EnableRobot` | 同一事实写三遍：另有 `OpenRobot` 记录存在性 + 其 `Status` |
| `EnableWebhook` | 同上；且它的"真相表"也已删除 |
| `EnableOAuth` | 同一事实写两遍：另有 `OpenOAuthConfig` 记录 + 其 `H5/Desktop/Mobile.Enabled` |
| `Category` | 枚举却用 `varchar` 存，且暂无应用市场 —— 需要时再加 |
| `LastModifiedBy` | 应用只有唯一 Owner，修改人恒等于 Owner → 可推出 |
| `Version` | 孤儿字段，说不清描述什么事实 |

第三轮 · 类型与审核流程：

| 字段 | 删的理由 |
|---|---|
| `AppType` | 见下节"为什么不用 `AppType` 分 bot/oauth/robot" |
| `AuditStatus` / `AuditedBy` / `AuditedAt` | 审核流程三件套。**应用创建即启用，不存在"待审核/已拒绝"** —— 在当前形态下这三个字段没有产生者 |

**为什么不用 `AppType` 分 `bot` / `oauth` / `robot`**

你提的这三种**确实就是海狸的全部能力**，但**不该由一个字段来表达**：

| 问题 | 说明 |
|---|---|
| **它是"能力的第二份真相"** | "这个应用是 robot" ⟺ `OpenRobot` 里有它的记录。再存一个 `AppType=robot`，就多了一份要同步的数据 —— 正是刚删掉的 `EnableRobot` 那类问题 |
| **它挡不住叠加** | 一个应用完全可以既提供登录、又挂机器人（钉钉、飞书都允许）。单个枚举值表达不了"兼具" |
| **原语义（自建 / 第三方）也失去用途了** | 那个区分的唯一作用是"决定要不要审核" —— 审核流程已删 |

→ **删掉。** "这个应用能做什么"看能力表有没有记录，一眼即知。

**能力不在这里表达（三种能力各有各的表）**

| 能力 | 对应的表 | 是什么 |
|---|---|---|
| 通知机器人（bot） | `OpenBotModel` | 单向推送：靠 `Token` 往群里推消息，**不能对话** |
| 登录（oauth） | `OpenOAuthConfig` | OAuth 登录配置（H5 / 桌面 / 移动三端） |
| 智能机器人（robot） | `OpenRobot` | 双向对话：能收事件、能回消息，可被 @ |

> **连带影响（已处理）**：审核流程删掉后，`OpenDeveloper` 也从「申请 + 审核」变成「**开发者登记**」—— 保留该表，删掉全部流程态字段（见 3.8 节）。


### 3.2 `OpenAppSecurity`（应用安全配置）· **已整表删除**

**这张表走了一个典型过程：先砍到 3 个字段，再看它是否还值得存在。**

**第一轮**，砍掉 5 个"维度不对"的字段：

| 字段 | 删的理由 |
|---|---|
| `CSRFProtection` | CSRF 是**浏览器会话**的安全问题。开放平台 API 是**服务端调用**（`appId` + `appSecret`），压根没有浏览器会话 → 场景不存在 |
| `AllowedOrigins` | CORS 同理，是**浏览器**的限制；且属网关职责 |
| `RequireHTTPS` | **部署/网关**维度，不是应用属性 |
| `TrustedDomains` | 可信域名是**客户端微应用（JSSDK）**维度 |
| `RateLimitEnabled` | **冗余**：`RateLimitQPS = 0` 即"不限制"，可推出 |

**第二轮**，剩下 3 个字段再判一次：

| 剩下字段 | 再判断 |
|---|---|
| `AppID` | 外键 —— 没有内容可指向，自然失去意义 |
| `IPWhitelist` | IP 白名单是**网关职责**（网关统一配，不必 per-app 各存一份） |
| `RateLimitQPS` | 限流同理，属**网关配额策略** |

→ 三个里两个该**下沉到网关层**，剩下一个外键。**表的存在理由不成立 → 整表删除。**

> 这一节的价值：**先删到只剩骨架，再看它是否还值得存在。** 很多冗余表都是这样暴露出来的 —— 而不是靠"感觉这张表没用"。

### 3.3 `OpenRobot`（智能机器人）· 8 → 3 字段，并由 `OpenAppRobot` 改名

本表**收敛成纯归属关系表**：

| 保留 | 说明 |
|---|---|
| `AppID` / `RobotID` | 归属关系（`RobotID` 即 IM 用户ID） |
| `Status` | 机器人是否启用 |

**删掉 5 个**（分两轮）：

| 字段 | 删的理由 |
|---|---|
| `RobotName` / `Avatar` | 昵称头像属 `UserModel`（见零节第 1 行） |
| `CommandPrefix` | 命令前缀意味着**平台要解析命令**，但平台只转发、不解析 |
| `EnableSingleChat` / `EnableGroupChat` / `EnableAtMention` | **平台只负责把消息送达，不替机器人决定"该不该响应"。** 要不要在单聊/群聊里回复，是机器人（agent）自己的策略 —— 它收到消息自己忽略即可，不需要平台来拦 |
| `WelcomeMessage` | 同理：机器人的对外表达（欢迎语、打招呼）属于机器人自己 |

> **判断依据**：一个字段如果描述的是"**机器人打算怎么做**"，它就不该待在平台侧。
> 平台侧只该有"**这个机器人在 IM 里是谁、开没开**"。

### 3.4 `OpenOAuthConfig`（OAuth 配置）· 9 → 8 字段，并由 `OpenAppOAuth` **改名**

| 删的字段 | 理由 |
|---|---|
| `RedirectURIs`（顶层） | 与 `H5OAuth.RedirectURIs` **同一概念存两份**。Desktop / Mobile 用的是 `CustomScheme`，不会用 redirect URI → 顶层那份完全被 H5 覆盖 |
| `H5OAuth.JsSdkDomains` | JSSDK 域名白名单属**客户端微应用**维度，随它独立成表 |

**类型统一**：`H5` / `Desktop` / `Mobile` 的 JSON 列 `type:text` → `type:json`（与 `OpenBotModel.Security` 一致）

**改名理由**：原名 `OpenAppOAuth` 把「归属」（App）和「内容」（OAuth）混在一个名字里。
**表名该描述"它是什么"，归属交给外键 `AppID` 表达。** 改名后 OAuth 家族齐了：

```
OpenOAuthConfig   ← 配置
OpenOAuthCode     ┐
OpenOAuthToken    ├ 运行时数据
OpenOAuthQrCode   ┘
```

### 3.7 `OpenOAuthCode`（授权码）· 13 → 9 字段

| 删的字段 | 理由 |
|---|---|

| 角度 | 说明 |
|---|---|
| **职责归属** | 发消息幂等是**调用方**的责任 —— 第三方该自己保证"不重复发"，平台不必替它兜底 |
| **成本** | 这张表没有 TTL，会随调用量无限增长；它唯一的作用（防重复）收益小于长期维护成本 |
| **判据** | 它描述的是"**别人打算怎么调我**" —— 与 `OpenAppSecurity`（平台替别人决定）同类，属平台越界 |

> **代价（需知晓）**：第三方若因网络重试而重复调用 `send_message`，平台不再去重 —— 这要靠调用方自己保证幂等。

### 3.11 `OpenOAuthConfig` 内嵌三结构

`H5OAuth` / `DesktopOAuth` / `MobileOAuth` 是 **JSON 内嵌值对象**，非独立表 —— ✅ 合理。
（已删 `H5OAuth.JsSdkDomains`，理由见 3.4。）

### 审查尺子（固化，后续每张表都按这个）

> **这个字段描述的事实，能不能从别处推出来？**
> - 能推出来 → 派生冗余 → **删**
> - 推不出来 → 独立事实 → 留（但要检查类型/约束配不配得上）

## 六、附：接入 agent（OpenClaw / 自研 agent）的数据表就绪情况

> 背景：目标是让 agent 通过**长连接**接入海狸 IM（替代 webhook）—— IM 的消息送达 agent、agent 的回复回到 IM。
> **结论：`open_models` 不需要为此做任何调整。** 前几轮删掉 webhook 那两张表，正好给长连接让出了位置。

### 接入 agent 需要的数据，全都已经在了

| 需要什么 | 靠什么表达 | 状态 |
|---|---|---|
| agent 的身份凭据 | `OpenApp.AppID` + `AppSecret` | ✅ |
| agent 在 IM 里是谁 | `OpenRobot.RobotID`（即 IM 用户ID） | ✅ |
| agent 能不能用 | `OpenRobot.Status` | ✅ |
| 谁有资格创建应用 | `OpenDeveloper` | ✅ |
| 回复消息 | `robot/v1/send_message`（**接口**，不需要表） | ✅ |

### 为什么长连接比 webhook **更少**需要表

| 需要的东西 | webhook 模式 | 长连接模式 |
|---|---|---|
| 投递地址 | 存 `CallbackURL` | **不需要** —— 连接本身就是地址 |
| 验签密钥 | 存 `Secret` | **不需要** —— 连接已鉴权 |
| 投递结果 | 记 `OpenWebhookLog` | **不需要** —— 没连上就是"对方离线" |
| 连接状态 | — | **放内存**，不落库（连接是瞬时的） |

→ 长连接是"**更少的数据表**"。所以删掉 `OpenAppEventSubscription` / `OpenWebhookLog` 是**给长连接让路**，不是砍功能。

### 一个已确认的点：`OpenRobot` 的 1:1 够用

`OpenRobot.AppID` 是 `uniqueIndex`（1 应用 : 1 机器人）。

已核实 agent 侧**按 `user_id` 隔离**（`agent_message.user_id` / `agent_memory_fact.user_id` / `agent.user_id`）
—— 即**一个 agent 服务所有用户**，用 `user_id` 区分会话与记忆。

所以不需要"每个用户一个机器人"（那样得建 N 个应用）。**1:1 够。**

### 逐项排除"要不要新增表"

| 候选 | 结论 |
|---|---|
| 连接状态表 | ❌ 不需要 —— 内存注册表（按 `RobotID` 索引）即可 |
| 事件订阅表 | ❌ 不需要 —— 长连接**连上即收全部**；要过滤哪些消息由 agent 自己判断（符合"平台不替别人做决定"） |
| 推送日志表 | ❌ 不需要（已删） |
| 机器人读消息历史 | ❌ **不是表缺口** —— 是**接口**缺口（用 `chat` 域已有的消息表） |

### 唯一的设计选择：断线期间的消息怎么办

| 方案 | 要不要加表 | 说明 |
|---|---|---|
| **A. 机器人重连后自己拉**（推荐） | ❌ 不加 | IM 本来就有消息存储；agent 用"最后收到的消息 ID"作起点补拉 |
| B. 平台补推 | ✅ 要加事件表 + 游标 | 平台记录"推送到哪了"，重连后按游标补发 |

### 所以真正要做的事（都不在 `open_models`）

1. **`open_bot_api` 长连接服务** —— 承接 `GET /api/open_bot/v1/ws`
2. **机器人"读消息历史"接口** —— agent 补上下文 / 断线补拉
3. （可选）断线补推策略

**一句话**：数据表这块已经就绪 —— 现在缺的是**服务**和**接口**，不是表。
