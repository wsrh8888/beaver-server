## 评价 utils/beaverlog 日志模块（只读诊断，未改代码）

代码规模：beaverlog 仅 2 个文件（logger.go / model/log_msg.go），被 app 下 370 个文件使用、共 813 处 Info/Warn/Error 调用。

排查结论（按严重度）：

1. **caller 全部指向封装层** —— logx v1.7.4 的 richLogger 用 `getCaller(4 + callerSkip)` 写 caller 字段，beaverlog.send 多包一层导致 caller 恒为 `utils/beaverlog/logger.go:97/99/101`。
   已用临时 demo（go run）实测验证：未修复 caller=封装函数行，加 `WithCallerSkip(1)` 后正确指向调用方。修复只需一行：`lg := logx.WithContext(ctx).WithCallerSkip(1)`。
2. **circle_api / circle_rpc / agent 从未调用 beaverlog.Init** —— circle 有 35 个文件在用，source 字段恒为空串。Init 是全局单例 + 手动调用，编译期拦不住。
3. **日志落盘配置只有 auth_api / auth_rpc 配了 `Mode: file` + Path + KeepDays:7**，其余 26 个服务只配了 Encoding/TimeFormat，走默认 console → stdout，无轮转。agent_* 连 Level 都没配。
4. **trace 链路只在 3 个服务存在** —— HTTP: auth_api / user_api / open_api 挂了 TraceMiddleware；gRPC: 只有 auth_rpc / user_rpc 挂了 TraceServerInterceptor。logx.WithContext 靠 ctx 里的 `logx.fieldsContextKey`（由 common/traceid.WithContext 注入）才有 trace/clientUuid，26 个服务该字段为空，跨服务串联断了。
5. **chat_rpc 挂的 RequestLogInterceptor 会全量 json 序列化 req/resp** —— 聊天正文落盘，且高频路径 IO 压力大；utils.LogRequest 无任何脱敏钩子，若挂到 auth_rpc 则密码/验证码/token 明文进日志。
6. Warn 走 `Sloww`，而 logx v1.7.4 里 slow 的闸门是 `shallLog(ErrorLevel)`，且 go-zero 无 warn 级别（仅 debug/info/error/severe），告警按 warn 分级会落空。
7. 无 Debug 级、无动态调级；370 个 Logic 手动初始化 logger 字段，漏一个即 nil pointer panic。
