- 核对纠正：用户以为子类型被多接口复用，实际 CircleItem/BotItem/MomentItem/DocItem/AgentItem 全是**一对一**引用（我在提问时说法不准），归位即可、无需复制。唯一真共享的是 agent 的 `Reply`（两接口都返回）→ 按"不共享"拆成 `SendMessageRes` / `ListConversationsRes`，各自保留 code/msg/resultJson 字段 + GetCode()/GetMsg()；remote/agent 的 `post` 改泛型 `post[Res any]` 解码到对应 Res。

- 规范落地：`skills/beaver-dev/references/go-zero-server.md` 在 Remote 章节新增「types/remote DTO 契约（强制）」：一接口一组 type 块、禁跨接口共享、对端统一回包要拆、token.go 例外。

## 第三轮：agent 公共回包抽 response.go + remote 拆文件（用户纠正）
- 用户纠正：第二轮把 agent 的 Reply 拆成两份独立 Res 不对。正确做法——每接口仍保留 Req+Res 配对（不能只剩 Req），但公共回包抽到 `types/remote/agent/response.go` 按类别分组定义一次，各 Res 以匿名字段嵌入 Reply，公共字段 code/msg/resultJson 只维护一处。
- 关键事实（决定 agent 不能套 ajax）：`types/remote/agent` proto JSON 是 `{code,msg,resultJson}`（result_json），不是 go-zero 的 `{code,msg,result}`；`utils/ajax/ajax.go:153-182` 的 decode 只认 result 字段、code!=0 转 StatusError（StatusError 解不了 resultJson）。故 agent 必须自管解码（remote.go 的泛型 post）。用户贴 StatusError 以为底层已兼容——实际底层只兼容标准信封，agent 属对端不遵守标准的例外。
- 落地：agent.go 每接口一组 type 块 Req+Res，Res 嵌入 Reply；response.go 按"类别一：对端统一回包"组织 Reply+GetCode/GetMsg；remote/agent 拆文件对齐 open——remote.go 只留 post/truncate 通道，业务方法拆到 sendmessage.go / conversation.go。
- 规范更新 go-zero-server.md：公共回包条款改为"抽 response.go + 各 Res 嵌入 + 通道按信封选（标准走 ajax.Post[Res]，非标准自管泛型 post[Res]）"；新增硬性第 8 条"remote.go 只放通道 plumbing，业务方法一律拆到独立 <biz>.go，静态 token 对端同样照拆"。
- 编译 EXIT=0；调用方 reply.Code/reply.ResultJson/reply.GetCode() 经匿名嵌入提升仍可访问。
